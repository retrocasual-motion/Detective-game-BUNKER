**Статус:** предложение от 06.11.2026 (исследование по разделу 14 `TECH_PLAN.md` v2).

## 1. Критерии (из технического плана)

- Только браузер на компьютере, экран от 1366×768; быстро и плавно.
- Много медиа: ~95 фото, ~22 аудио + радиозапись 15 суток, 10 видео, 6 3D-моделей,
  12 сайтов, сотни страниц документов.
- Правила, пароли, рубрика, закрытые материалы — **только на сервере** (P-10).
- Каналы доставки с двумя режимами (P-14): почта, телефон, сайты.
- Аудитория — Россия (русский язык, российские номера, S-4): хостинг, почта, оплата,
  телефония должны работать в РФ; персональные данные россиян (почта) — в БД в России
  (152-ФЗ, ч. 5 ст. 18; штрафы выросли с 30.05.2025).
- Контент живёт в пакете игрока (`playtest/packs/<версия>/`) и меняется без
  программиста.

## 2. Язык и структура кода

**TypeScript везде.** Один язык для клиента, сервера, движка и сборки контента.
Строгий режим типов — меньше ошибок «на ходу», которые иначе нашёл бы только игрок.

**Монорепозиторий (pnpm workspaces):**

| Пакет | Что внутри |
|---|---|
| `engine` | движок правил: перенос `access.json`, без интерфейса; запускается на сервере; сквозные проходы — его тесты |
| `content` | сборка контента из пакета игрока: материалы, правила, письма, сайты → проверенный JSON + список медиа; проверка утечек (P-10) |
| `api` | сервер: вход, состояние игрока, движок, каналы доставки, очередь писем |
| `game-web` | клиент игры |
| `sites` | 12 сайтов реального слоя (Astro) |

**Где хранить код — вопрос автору (раздел 12):** в этом репозитории в `game/` или в
отдельном. Медиа в git не кладём ни в одном варианте — только в хранилище.

## 3. Клиент

**React + Vite** — рекомендация.
- React — самая большая экосистема ровно под наши задачи: React Three Fiber (3D),
  use-gesture (перетаскивание и масштаб), Motion (переходы), wavesurfer.js (шкала аудио).
- Vite — быстрая сборка и мгновенное обновление страницы при правке кода.
- Состояние — Zustand (просто и быстро); данные с сервера — TanStack Query.

**Почему не другое:**
- **Next.js** — силён для сайтов с SEO; игра за входом, SEO не нужно, а серверный
  рендеринг добавляет сложность. Лендинг (главная страница) — отдельно, на Astro.
- **Svelte / SvelteKit** — легче и быстрее на старте, но меньше готовых библиотек для
  3D и жестов; React надёжнее на длинной дистанции.
- **Игровые движки (Phaser, Unity WebGL, Godot)** — сильны в спрайтах и физике, слабы в
  том, что у нас главное: документы, выделение текста, вёрстка бумаги, окна. Unity
  WebGL ещё и тяжёлый на загрузке.

## 4. Стол и доска

**Свой холст на DOM + CSS transform.** Весь стол — один контейнер, который двигается и
масштабируется трансформацией (видеокарта делает это плавно); объекты — элементы с
миниатюрами; невидимые за краем экрана не рисуются. Нити доски — слой SVG.
- Для наших 150–300 объектов этого достаточно; плюс — текст и интерфейс остаются
  обычной вёрсткой (выделение, шрифты, доступность).
- Слой отрисовки держим отдельным модулем: если на слабых ноутбуках будет рвать —
  меняем на **PixiJS** (WebGL; в отчётах держит десятки тысяч карточек), не трогая
  остальную игру.

**Почему не готовые доски:** tldraw — коммерческое использование только по платной
лицензии (цена — через отдел продаж); Konva — Canvas 2D, выигрыша над DOM на нашем
объёме нет, а текст пришлось бы рисовать вручную.

## 5. Документы, сканы, поиск

- **Документы** — HTML/CSS «бумага»: бланк, печать, подпись, следы обращения (сгибы,
  продавленный карандаш — картинками-слоями). Выделение строки → «В ходатайство» —
  нативное выделение браузера.
- **Сканы, рукописи, фото** — изображения AVIF/WebP в нескольких размерах (миниатюра на
  столе, экран, оригинал). Крупные сканы с мелкими деталями — глубокий зум
  (OpenSeadragon: картинка режется на плитки, грузится только видимое).
- **Поиск по документам** — индекс в браузере (MiniSearch или FlexSearch) **только по
  открытым игроком текстам**: закрытое в браузер не попадает.

## 6. 3D-предметы

**three.js через React Three Fiber + drei** — вращение мышью, приближение, активные
точки (клик по уголку бланка в клапане папки). Модели — glTF/GLB, сжатие геометрии
Meshopt и текстуры KTX2 (gltf-transform в сборке): модель грузится за доли секунды.
Простая альтернатива — веб-компонент `<model-viewer>`, но в нём меньше контроля над
активными точками и светом.

## 7. Аудио и видео

- **Короткие записи** (голосовая почта, диктофон, линии, кассета) — Web Audio API;
  шкала, метки игрока — wavesurfer.js.
- **Радиозапись 15 суток (раздел 4.8 плана).** Файла на 15 суток нет: сервер отдаёт
  список событий открытого окна времени и короткие клипы; фон (гул, эфир округа, помехи)
  генерирует и зацикливает браузер через Web Audio. Перемотка на «13.10 08:44» —
  вычисление позиции, а не загрузка.
- **Видео** (до 1:40) — MP4 (H.264; где поддерживается — AV1/WebM) с докачкой по
  частям; потоковый HLS не нужен.
- **Закрытые медиа** — ссылки с подписью и сроком жизни, выдаются сервером после
  открытия материала.

## 8. Сервер и данные

- **Node.js + Hono** — лёгкий быстрый сервер на TypeScript; альтернатива — Fastify.
- **PostgreSQL** + **Drizzle ORM** — состояние игроков, журнал действий, черновики,
  раскладка, письма. Схема — типизирована, миграции — в репозитории.
- **pg-boss** — очередь отложенных задач в той же базе: «через минуту отправить ответ
  бюро». Отдельный Redis не нужен.
- **Better Auth** — вход ссылкой на почту (T-14-A); данные входа в нашей БД (152-ФЗ).
- **Движок на сервере.** Клиент отправляет действие («отправить ходатайство: поля,
  карточки»), сервер прогоняет правила и возвращает только результат.

## 9. Хостинг, хранилище, CDN — в России

**Почему в России:** (1) 152-ФЗ — почты игроков-россиян в БД в РФ; (2) с 09.06.2025
российские провайдеры замедляют Cloudflare (грузятся первые 16 КБ), на ноябрь 2026 не
снято — поэтому никакого Cloudflare для игры и сайтов; (3) скорость для игроков в РФ.

- **Прототип (M0):** один VPS в России (Selectel, Timeweb Cloud или Yandex Compute) с
  Docker Compose: Postgres + сервер + статика + сайты. Дёшево, просто, всё в одном
  месте; ежедневная копия базы.
- **Релиз:** Yandex Cloud (управляемый PostgreSQL, контейнеры, Object Storage, CDN,
  Postbox — один поставщик) или Selectel (облако + S3 + CDN). Цены и бесплатный уровень
  — проверить в калькуляторе перед выбором.
- **Медиа:** S3-совместимое хранилище в РФ + российский CDN; ссылки с подписью.
- **Мониторинг ошибок:** GlitchTip (совместим с Sentry, ставится на свой сервер) или
  средства облака; внешний Sentry — передача данных за границу.

**GitHub Pages** годится только для статики и стоит за рубежом — для игры не подходит;
для сайтов реального слоя лучше тот же российский хостинг.

**Сравнение цен VPS 2 vCPU / 4 ГБ (обзоры 2025–2026, проверить на сайтах перед покупкой):**

| Поставщик | Цена в месяц (ориентир) | Что ещё | Для чего |
|---|---|---|---|
| **Timeweb Cloud** | ~1000–1900 ₽ (50 ГБ NVMe) | S3-хранилище, базы, заявленная доступность 99,98 % | **прототип (рекомендую)** — дешевле всех, всё в одном кабинете |
| Selectel | ~3600 ₽ (+8–9 % с 01.2026) | сильная репутация дата-центров, S3, CDN, управляемые БД | релиз |
| Yandex Cloud | ~5000 ₽ (близкая конфигурация, +3–8 % с 05.2026) | управляемый PostgreSQL, CDN, Postbox, контейнеры | релиз |

## 9a. Домены и сайты реального слоя

**Сколько доменов нужно.**
- **Прототип — ноль новых.** Все 12 сайтов и сама игра живут на поддоменах домена автора
  (например, `vaultline.<домен>.ru`, `game.<домен>.ru`); письма уходят с адреса на том же
  домене.
- **Релиз — 12 доменов сайтов** по канону (vaultline-program.com, hexon-bio.com,
  okrug-bureau.org и т. д., раздел 4.13 плана): адрес на чужом домене выдал бы игру.
  Домен бюро `okrug-bureau.org` нужен ещё и как адрес отправителя писем бюро.
  Ориентир цены: .ru — около 1000 ₽ в год; .com/.net/.org у российских регистраторов —
  порядка 1500–2000 ₽ в год за каждый (уточнить у REG.RU / RU-CENTER); 12 доменов —
  примерно 18–24 тыс. ₽ в год.
- **Домен самой игры** (лендинг и вход) — по желанию: свой брендовый (например, по
  названию игры) или поддомен сайта автора.
- **Свободны ли канонические имена — проверить у регистратора до покупки.** Короткие
  общие имена (mailbridge.net, coltonsupply.com, sentinel-labs.net) могут быть заняты; если
  занято — новый адрес означает правку канона (адрес стоит в материалах), это решение
  автора. Покупать лучше все разом, когда тексты материалов будут окончательными.

**Сервис «много сайтов за одну плату».** Конструкторы вроде Tilda не подходят: (1)
сайты должны собираться из того же текста, что и снимки страниц в деле — иначе снимок
и сайт разойдутся; (2) архив газеты и эпилог требуют связи с игровым сервером; (3)
полный контроль над noindex и видом «2009 года». Бесплатный путь проще: **наш же VPS
отдаёт все 12 сайтов** (один веб-сервер, по сайту на домен) — без доплаты, платим
только за домены.

## 11. Сборка контента и тесты

- **Сборка контента** (`content`): скрипт читает пакет игрока (md + `access.json`),
  проверяет схему (Zod), собирает JSON материалов, правил, писем, сайтов и список
  медиа; падает, если закрытое попало в стартовую часть (P-10). Автор правит тексты в
  md в репозитории — без программиста.
- **Тесты движка — Vitest:** правила по одному + сквозные проходы `walkthrough` (171
  действие) как регрессия: любое изменение правил прогоняется целиком.
- **Тесты интерфейса — Playwright:** сценарии «отправить ходатайство», «открыть
  ноутбук ключом», «решить дело»; скриншоты для проверки вида. Им же Claude проверяет,
  что кнопки нажимаются и всё работает, перед каждым PR.
- **GitHub Actions:** проверка типов, линтер, тесты на каждый PR; слияние — только при
  зелёных проверках.

## 12. Среда разработки

**Как будет устроена работа:** код всегда в GitHub. На каждую часть — своя ветка →
Claude пишет код и тесты, запускает игру и проверки → PR → автор смотрит → «мержим».

| Вариант | Как это выглядит | Плюсы | Минусы |
|---|---|---|---|
| **ENV-A (рекомендую): VS Code + расширение Claude Code + GitHub** | на компьютере автора VS Code с панелью Claude; Claude пишет код, запускает игру, тесты; автор сразу кликает игру в браузере | игра видна вживую, мгновенное обновление после правки; встроенные просмотр изменений, откат (checkpoints), план с комментариями; skills, плагины, MCP работают; код на GitHub | на компьютере ставятся Node.js, git, VS Code (один раз); в расширении — не все команды CLI (есть встроенный терминал) |
| **ENV-B: только облачные сессии (как сейчас)** | всё в браузере claude.ai/code или телефоне | ничего не ставить; работа идёт, даже когда компьютер выключен; удобно для длинных задач и параллельной работы; skills из репозитория работают | игру не покликать вживую так же просто (Claude проверяет её сам скриншотами Playwright); каждый запуск — свежий контейнер; нет `/plugin` |
| **ENV-C: GitHub Codespaces + расширение** | VS Code в браузере на сервере GitHub | полностью онлайн | платно после бесплатных часов; официальная поддержка расширением не подтверждена |

**Рекомендация:** ENV-A — основная среда для написания игры, ENV-B — в дополнение
(длинные фоновые задачи, работа с телефона, обсуждения и документы — как этот тред).
Сессию можно переносить: облачную — в терминал (`--teleport`), в VS Code облачные сессии
открываются во вкладке Web.

**Skills подхватываются везде одинаково, если лежат в репозитории** (`.claude/skills/`):
VS Code, терминал и облачные сессии читают их. Плагины из маркетплейса ставятся через
`/plugin` в VS Code или терминале; в облачных сессиях — плагины, включённые в аккаунте
claude.ai.

| **webapp-testing** | anthropics/skills | Claude сам открывает игру в браузере (Playwright), кликает, смотрит логи и скриншоты | **да** |
| **frontend-design** | anthropics/skills | качественная вёрстка интерфейса | да, на этапе интерфейса |
| **Context7** (MCP) | Upstash | актуальная документация библиотек прямо в работу — меньше ошибок по устаревшему API | **да** |
| **Playwright MCP** | Microsoft | управление браузером из Claude | да (или webapp-testing — одно из двух) |
| planning-with-files | уже стоит | план, находки, ход работы между сессиями | уже есть |

| свои skills проекта (сделать при старте) | этот репозиторий | `bunker-engine` (как устроены правила и как их менять), `bunker-content` (сборка контента), `bunker-playcheck` (прогнать сценарий игры в браузере) | **да** — главный источник «помнить весь контекст» |

**Честно о рисках:** много пересекающихся skills мешают друг другу (два способа
планировать, три способа тестировать). Берём минимум: один для процесса
(planning-with-files), один для дисциплины кода (Superpowers: TDD, отладка, проверка),
один для браузерных проверок (webapp-testing), Context7 для документации и свои skills
проекта. Остальное — только при конкретной нужде. Звёзды и «самые популярные» в
рейтингах — ориентир, не гарантия качества.
