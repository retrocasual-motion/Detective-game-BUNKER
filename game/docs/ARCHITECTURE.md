## Поток данных

```
пакет игрока (md) ──content build──▶ starting.json ──api──▶ GET /api/materials ──▶ клиент
                 └──────────────────▶ server.json (правила + закрытые) ─▶ engine (только сервер)
клиент ── POST /api/action ──▶ api ──▶ engine.act ──▶ player_progress ──▶ ответ + открытые материалы
                                                           GET/PUT /api/state  ◀─▶ клиент (раскладка)
                                                           PostgreSQL: player_state, player_progress
```

- **Материалы.** В браузер приходят стартовые и те закрытые, которые этот игрок открыл (P-10).
  Правила, тексты закрытых и правильные ответы — только в `server.json` на сервере.
- **Прогресс дела** (`Progress` движка: открытое, «видено», неверные попытки, почта
  специалиста, конец дела) — таблица `player_progress`; пишет только сервер. Клиент не может
  положить на стол неоткрытый материал (PUT → 400). «Видено» (форма заключения): всё, что
  открыли прошлые действия, доставлено их ответами — движок отмечает это на следующем
  действии (`act`, `autoSeen`); `GET /api/materials` только читает. Действия идут очередью
  в одном процессе (несколько процессов — этап 6, транзакция).
- **Состояние игрока** — один JSON (`PlayerState`, версия `STATE_VERSION` = 5): текущий вид
  («Стол» или «Стена») и стена: камера, вещи на стене (материал, персонаж «p:…» или записка
  «n:…»: место, наклон, порядок), нити (между вещами), записки и ярлыки игрока (текст).
  «Входящие» не хранятся: это открытое по ходу дела, но ещё не повешенное (`inboxIds`).
  Версия 4 переводится (снятые в поле листы и нити остаются), версии 1–3 — раскладка
  заново. Сервер проверяет схему и то, что все упомянутые вещи у игрока есть (P-10). При
  чтении `reconcile` убирает то, чего больше нет, и вешает недостающих персонажей и
  стартовые материалы на начальные места (`startSlot`).
- **Игрок пока один** (`player_id = 'local'`); вход и аккаунты — этап 6.

## API

| Маршрут | Ответ |
|---|---|
| `GET /api/health` | `200 {"ok":true}`; `503 {"ok":false}`, пока миграции не применены |
| `GET /api/materials` | стартовые материалы + открытые этим игроком (все `/api/*`, кроме health, отвечают 503, пока база не готова; клиент повторяет раз в секунду) |
| `POST /api/action` | `{action, target, value?, cards?}` → `{reply, released}` (+ `result` — вид итога, только в разработке): ответ правила и открытые материалы. ЗВОНОК — нет (телефонные линии — этап 6); ФИНАЛ и СТОП в production — нет (этап 5) |
| `POST /api/petition` | ходатайство из папки (этап 3): `{to, ask, basis}` (карточки `{file, quote}`) → `{n, delayMs}`; ошибка оформления (FORM-B: «не оформлено», 7 отказов-оформлений, лимит) — `422 {error}`, письмо не уходит. Общий отказ адресата (PRE-B, 5 правил `*-fail`) — `{refused}` сразу, без письма, попытка засчитана. Ответ — письмо `M00N` во «Входящих» через `MAIL_DELAY_MS`; до доставки ни письмо, ни вложения в `/api/materials` не попадают (P-10). В production ходатайство через `/api/action` не принимается |
| `GET /api/mail/pending` | `{inMs: [...]}` — через сколько мс придут письма в пути (клиент заглянет тогда) |
| `POST /api/dev/action-line` | только не в production (E2-CHECK-A): `{line: "ДЕЙСТВИЕ \| ЦЕЛЬ \| ЗНАЧЕНИЕ"}` → тот же движок |
| `GET /api/state` | состояние игрока (или по умолчанию) |
| `PUT /api/state` | `204`; неверная схема или чужой материал — `400`. Заголовок `x-state-seq` — номер версии: запрос старее уже сохранённого не применяется (старый ответ, пришедший позже, не затирает новый) |
| `DELETE /api/state` | сброс раскладки и прогресса (только не в production) — для автотестов |

В production (`WEB_DIST` задан) тот же сервер отдаёт собранный клиент; любой путь,
кроме `/api/*`, — `index.html`.

## Где что менять

- Новое поле состояния игрока → `shared/schemas.ts` (+ `defaultState`, `reconcile`); если старое сохранение без него не читается — поднять `STATE_VERSION` и научить `upgradeState`; тесты в `shared`.
- Комната: позы камеры, размер доски, перспектива → `room/camera.ts`; стены, рама, стол, предметы на столе → `room/decor.ts`; куда ведут стрелки → `room/views.ts`.
- Стена: начальная раскладка и край доски → `shared/src/layout.ts`; персонажи → `shared/src/persons.ts`; лоток «Входящие» на столе → `room/decor.ts` (`inboxObjects`).
- Новый маршрут → `api/src/app.ts`, тест в `api/test/`.
- Новая таблица → `api/src/db/schema.ts`, затем `pnpm -F @bunker/api db:generate` (миграция в `api/drizzle/`).
- Внешний вид → только `theme/tokens.css` и `app.css`.
- Какие материалы — устройства → `content/src/build.ts` (`EVIDENCE_IDS`); форма на столе — `KIND_BY_ID`, `lockedKind`.
- Правила дела меняются в пакете (`gm/access.json`, собирает `gm/build_access.py`), не в коде; после правки — `pnpm content:build` и `pnpm -F @bunker/engine test` (сквозные проходы).
- Новое действие движка → `engine/src/engine.ts` (`act`) и схема `ActionSchema` в `api/src/app.ts`.
