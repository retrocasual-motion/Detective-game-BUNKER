## S1

### 2a-1 · S1 · `api/src/app.ts:469-478`, `game-web/src/save.ts:49-52` · номер сохранения — часы устройства, а сервер молча выбрасывает «старое» с ответом 204

`seq` клиент берёт как `Date.now() * 1000` (счётчик живёт только до перезагрузки страницы).
Сервер пишет состояние, только если новый `seq` больше сохранённого (`setWhere`), но в любом
случае отвечает `204` — клиент показывает «сохранено».

**Сценарий.** Игрок играл на устройстве A, у которого часы спешат на час (или на телефоне с
ручным временем). Продолжил на устройстве B с верными часами. Целый час все сохранения с B
приходят с меньшим `seq`: сервер отвечает 204 и ничего не пишет. Игрок закрывает вкладку —
час работы (стена, нити, блокнот, вскрытые конверты) пропал, ошибок не было. То же на одном
устройстве: часы стояли вперёд, система их поправила, страницу перезагрузили.
Вариант со злым умыслом не нужен, но есть: один запрос с `x-state-seq: 9007199254740991`
навсегда замораживает сохранение игрока.

**Уверенность:** подтверждено (`api.mts`, шаг A: два PUT → 204 и 204, в базе осталось первое,
«спешащее»).

**Направление.** Номер версии выдаёт сервер (счётчик в строке `player_state`), клиент шлёт
«я правил версию N»; несовпадение — 409 с понятным сообщением, а не тихое 204. Часы клиента в
порядке сохранений не участвуют.

### 2a-2 · S1 · `shared/src/layout.ts:229-232`, `api/src/app.ts:295-297`, `game-web/src/store.ts` (`load`) · сохранение, не прошедшее схему целиком, заменяется начальным и тут же затирается

`upgradeState` разбирает всё состояние одной схемой: одно неподходящее поле — `null`. Сервер
тогда отдаёт `defaultState`. Клиент при загрузке видит, что нет `started`, делает
`updateState` — и через 500 мс начальное состояние уходит на сервер с новым `seq`. Прежнее
сохранение уничтожено без следа и без вопроса игроку.

**Сценарий 1 (откат).** Выкатили версию с новым конвертом/полем, игроки поиграли, версию
откатили. У всех, кто вскрыл новый конверт (сейчас это `seized`, добавлен 25.11), `opened`
не проходит `z.enum(CONTAINER_IDS)` старого кода → начальное состояние → затирание.
**Сценарий 2 (переименование).** Конверт или вид окна переименовали/убрали
(`opened`, `PcWindowSchema.kind`, `LapWindowSchema.kind`, `ExcerptPlaceSchema.kind`,
регулярки `taken`/`pieces`/`joined`) — все сохранения с прежним значением стираются при
первом заходе. **Сценарий 3 (ужесточение предела).** Любой `max()` уменьшили.
История `schemas.ts` в версии 5 пока только расширялась (проверено по `git log -p`), поэтому
сегодня живых поломок нет — но защита держится на аккуратности, а не на коде.

Попутно: объект Zod молча отбрасывает неизвестные поля. Сохранение новой версии, прочитанное
старым кодом (откат, старая вкладка после выкладки), теряет новые поля без ошибки.

**Уверенность:** подтверждено (`api.mts`, шаг E: в базе блокнот и `opened: ['protocols','vault']`
→ GET отдал начальное состояние без блокнота; `layout.mts`: версия 6 → `null`). Затирание
клиентом — вывод по `store.ts` (`load` → `started`).

**Направление.** (1) Перед заменой начальным — копия нечитаемой строки в отдельную таблицу
или колонку. (2) Разбор по частям: стена, стол, блокнот, окна устройств — каждая часть
отдельно; не прошла — отбросить её, а не всё. (3) `.catch()` на перечислениях в массивах
(`opened`), чтобы неизвестное значение выпадало одно.

## S2

### 2a-3 · S2 · `engine/src/engine.ts:117-135`, `api/src/app.ts:164-172` · лимит попыток обходится добавкой слова в цель

Лимит считается по цели, которую присылает клиент, а `unlimited` — регулярки, которые ищутся
в любом месте цели. Правило при этом выбирается по той же цели поиском подстроки. Цель
«телефон газета» подходит и правилу телефона, и шаблону «газет» из списка без лимита.

**Сценарий.** `POST /api/action {action:'ПАРОЛЬ', target:'телефон газета', value:'0000'}` и
дальше по кругу: промахи не записываются, паузы нет. На настоящем пакете код телефона
подобрался на 111-й попытке за 3 мс, материал L540 открыт. То же для любого поля ПАРОЛЬ
(ноутбук, почта, архив HEXON, вход VAULTLINE): закрытые материалы достаются перебором, а не
расследованием — это обход P-10 «с чёрного хода». Вторая дыра той же природы: счётчик
промахов ведётся по первому правилу, чья цель подошла (`fieldRule`), а не по тому полю, куда
реально подбирают, — цель «сеанс телефон» считает промахи на поле «сеансы», которое без
лимита.

**Уверенность:** подтверждено (`limit.ts`: «телефон» → отказ, отказ, отказ, лимит; «телефон
газета» → 12 отказов подряд, `fails: {}`; перебор → успех `pw-phone`, открыто `L540`).

**Направление.** Клиент присылает не свободную строку цели, а идентификатор поля из закрытого
списка (как уже сделано у сайтов через `formAction`); сервер сам подставляет цель. Лимит и
«без лимита» привязать к идентификатору поля. Сверху — общий предел запросов действий на
игрока в минуту.

### 2a-4 · S2 · `api/src/app.ts:462-480, 501-506` · «Новое дело» не отменяет сохранения старого дела

`PUT /api/state` не знает, к какому делу относится состояние. После «Нового дела» строка
удалена, `seq` начинается заново — любое запоздавшее сохранение старого дела принимается.
К тому же PUT идёт мимо очереди `serial`, в которой стоит сброс.

**Сценарий.** Игра открыта на ноутбуке и на телефоне (или в двух браузерах:
`BroadcastChannel` видит только вкладки одного браузера). На ноутбуке — «Новое дело». На
телефоне игрок двигает лист — старое состояние уходит на сервер. В новом деле: вскрытые
конверты, старый блокнот, записки, нити, черновик заключения, `started`. Материалы, открытые
в старом деле, `reconcile` со стены уберёт, остальное останется. Если на стене старого дела
висели L-материалы — PUT получит 400, и вторая вкладка покажет «дело изменилось в другом
месте» (это как раз правильный исход, но случайный).
Узкий вариант той же гонки в одной вкладке: PUT уже прочитал прогресс, сброс прошёл, PUT
вставил строку.

**Уверенность:** подтверждено (`api.mts`, шаг B: после `/api/new-case` PUT старого состояния
→ 204, GET отдаёт старый блокнот и `opened: ['protocols','scene','seized']`).

**Направление.** Номер дела (поколение) в `player_progress`/`player_state`; клиент шлёт его с
каждым PUT, сервер отвечает 409 на чужое поколение. PUT и сброс — в одной очереди игрока.

### 2a-5 · S2 · `api/src/app.ts:462-480` · два устройства: последний записавший затирает всё состояние целиком

Состояние — один JSON, сервер не сверяет, от какой версии клиент его правил.

**Сценарий.** Дело открыто дома на компьютере (вкладка осталась) и на телефоне в дороге. На
телефоне игрок час раскладывает стену. Дома трогает один лист в старой вкладке — её состояние
часовой давности целиком ложится поверх. Ошибок нет. Защита «дело открыто в другой вкладке»
работает только внутри одного браузера, и даже там есть щель: новая вкладка читает состояние
раньше, чем старая досылает последние 500 мс.

**Уверенность:** вывод (сервер принимает любой PUT с большим `seq`; сценарий B это же
показывает).

**Направление.** То же, что в 2a-1: версия от сервера и 409 «состояние новее вашего» →
клиент перечитывает. Отдельно стоит решить, нужна ли игра с двух устройств сразу.

### 2a-6 · S2 (сработает при переезде) · `api/src/login.ts:33-39, 145-146` · предел писем «с одного подключения» за обратным прокси — один на всех

`clientIp` берёт адрес сокета. За прокси (а он нужен для HTTPS и поддоменов сайтов) это адрес
прокси: 10 писем входа в час на всех игроков вместе, 11-й получает «Слишком много писем».
Общий предел 300 в час к тому же позволяет чужому человеку с нескольких адресов закрыть вход
всем на час.

**Сценарий.** Плейтест на людях: 15 человек приходят в один вечер — пятеро не могут войти.

**Уверенность:** вывод (комментарий в коде сам это признаёт: «когда прокси появится»).

**Направление.** Адрес клиента — из заголовка прокси, с явной настройкой «доверять прокси»;
проверка при запуске в production, что настройка задана. Общий предел — в пересчёте на адрес
почты, а не один на сервер.

### 2a-7 · S2 · `api/src/env.ts`, `compose.yml:32-36`, `api/src/server.ts` · production запускается с небезопасными умолчаниями и не проверяет их

Проверки настроек при запуске нет. Что сейчас возможно молча:

- `compose.yml` по умолчанию `AUTH=off` и порт 8787 наружу: все посетители — один игрок
  `local`, любой жмёт «Новое дело» и стирает общее дело.
- `AUTH=link` в production без почтового сервиса: `MAIL_TRANSPORT` умеет только
  `mailpit`/`memory`/`none`. С `memory` письмо «отправлено», но никуда не ушло; с `mailpit`
  — 502. Войти нельзя никому.
- `PUBLIC_URL` по умолчанию `http://localhost:5173`: cookie без `Secure`, сайты дела не
  узнаются по хосту, ссылки в письмах ведут на localhost.
- Служебные маршруты (`/api/dev/login` — войти под любой почтой без письма;
  `/api/dev/outbox` — чужие ссылки входа; `/api/dev/action-line`; `DELETE /api/state`;
  ФИНАЛ/СТОП; вид итога `result`) закрыты одним условием `NODE_ENV === 'production'`.
  Сервер, выставленный наружу без этой переменной (туннель с `pnpm dev`), отдаёт вход в
  любое дело.

**Уверенность:** вывод по коду; в production служебные маршруты действительно закрыты
(тесты `login.test.ts`, `action.test.ts`).

**Направление.** Проверка при запуске: в production обязательны `AUTH=link`, `PUBLIC_URL` на
https, `SITE_SECRET`, рабочий почтовый транспорт — иначе сервер не стартует. Служебные
маршруты включать отдельным явным флагом (`DEV_ROUTES=1`), а не отсутствием `NODE_ENV`.

### 2a-9 · S3 · `api/src/app.ts:579-607` · страница сайта отдаётся без проверки, что именно она открыта

**Сценарий.** В пакете появляется правило АДРЕС с неякорным шаблоном (или шаблон

попадает в чужое правило → «успех» → сервер отдаёт текст L735, закрытый `requires`.

**Уверенность:** вывод. На нынешнем пакете утечки нет: все 13 шаблонов АДРЕС заякорены с
обеих сторон, перебор хвостов пути её не дал (`addr.ts`, `rules-meta.mjs`). Защита — в
пакете, а не в коде.

**Направление.** Перед отдачей — `has(main)` по прогрессу после действия; в `open` —
проверка, что `at.site.page` открыт.

### 2a-10 · S3 · `api/src/sites.ts:88-103`, `api/src/app.ts:550-567` · пропуск на сайты: не отзывается, не одноразовый, два вида неразличимы

Пропуск из ссылки (10 минут) и cookie сайта (30 дней) — одна и та же строка
`игрок.срок.подпись`, без вида, без привязки к сайту и к сессии.

**Сценарий.** Игрок вышел из игры на чужом компьютере. Вкладки сайтов дела ещё 30 дней
работают от его имени: читают открытые страницы и веб-почту, отправляют формы (тратят

деле. Ссылка с `?enter=…` из истории браузера годится повторно, пока не истекла, и прямо как
cookie.

**Уверенность:** подтверждено (`api.mts`: D1 — пропуск из ссылки как cookie → 200 со
страницей; D2 — один пропуск обменян дважды; D3 — после выхода игра 401, сайт 200).

**Направление.** В пропуск — вид (`enter`/`cookie`) и номер сессии или поколение дела;
проверять, что сессия жива. Пропуск из ссылки — одноразовый (отметка в базе или короче срок).

### 2a-11 · S3 · `api/src/db/schema.ts:62-67`, `api/src/app.ts:631-646` · очередь выписок: ключ общий на всех игроков, предела нет

Первичный ключ `pending_excerpts` — только `id`, который придумывает клиент;
`onConflictDoNothing`. Числа выписок в очереди никто не ограничивает.

**Сценарий 1.** Два игрока прислали выписку с одним `id` — вторая молча пропала (204).
Случайно при `crypto.randomUUID()` не случится, намеренно — да: зная чужой `id`, выписку

принял сохранение». Подтверждения нет, после перезагрузки очередь приходит снова — петля,
из которой игрок сам не выйдет. Та же петля у 301-й выписки с устройства.

принято 400, в очереди 400). Петля на клиенте — вывод по `store.ts` (`takeExcerpts`).

**Направление.** Ключ `(player_id, id)`; предел очереди на игрока; клиент не вешает сверх
предела схемы и говорит об этом.

Игрок, не переворачивавший ноутбук и даже не вскрывавший пакет, открывает

материалов, это станет прямой утечкой P-10. Второе: файл читается `readFile` целиком на
каждый запрос, без `Range`, `ETag` и `304` — для видео и звука это и память, и невозможность
перемотки.

**Уверенность:** вывод (выход за папку и чужие имена закрыты — тест `media.test.ts`).

**Направление.** У записи `MEDIA` — поле «какой материал должен быть открыт» (или «какой
конверт вскрыт»), проверка по прогрессу; имена закрытых медиа — только на сервере. Отдача
потоком с `Range`.

### 2a-14 · S3 · `shared/src/layout.ts:257-265, 293-311, 367-369` · старые сохранения: нити к устройствам пропадают, «потерянное» поле `desk` вскрывает пакет

**Сценарий 1.** Сохранение до 3D-стола: карточки устройств (24, 47–50) висят на стене, к ним
протянуты нити с подписями. После загрузки карточки уходят со стены на стол
(`DEVICES_ON_WALL = false`), нити к ним удаляются молча. Версия 4 «снятое и нити остаются» —
для таких нитей тоже неправда.
**Сценарий 2.** `seizedFromScene` считает сохранение старым, если поля `desk` нет. Вкладка со
старой сборкой (открыта до выкладки) шлёт состояние без `desk` — при следующей загрузке
пакет «Изъятое» оказывается вскрыт сам, а листы «Осмотра места» со стола — на стене в
начальной сетке.

**Уверенность:** подтверждено (`layout.mts`: «v5 без opened… нитей 0»; «поле desk потеряно»
→ `opened: ['scene','seized']`).

**Направление.** Нити к ушедшим карточкам — сохранить отдельным списком или предупредить
игрока один раз. Признак старого сохранения — явный (номер версии состояния), а не
отсутствие поля; после перевода — поднять `STATE_VERSION`, чтобы догадка выполнялась один раз.

### 2a-15 · S3 · `api/src/app.ts:137-154` · сервер проверяет ссылки только у стены

`invalidReference` смотрит вещи стены, нити и выписки. `desk`, `joined`, `taken`, `pieces`,
`turned`, окна устройств (`path`, `url`) не сверяются ни с материалами игрока, ни между собой.

**Сценарий.** Состояние с `joined: ['L990']` без самого L990 принимается; половина листа 51
после этого не висит ни на стене, ни во «Входящих» (`layout.mts`, шаг 9). Утечки нет
(`reconcile` чужое со стола убирает, тексты приходят только через `/api/materials`), но
состояние можно привести в вид, из которого игра сама не выходит. Обратная сторона:
`reconcile` и `invalidReference` — два разных списка правил, расхождение между ними даёт
вечный 400 на сохранении.

**Уверенность:** подтверждено для `joined`; остальное — вывод.

**Направление.** Одна функция «что у игрока есть» для `reconcile` и для проверки PUT; PUT
сохраняет результат `reconcile`, а не сырой ввод.

### 2a-16 · S3 · `api/src/app.ts:341-350, 451-454` · очередь действий — в памяти одного процесса

`serial` защищает прогресс только внутри процесса. Чтение-изменение-запись прогресса
(`loadProgress` → `act` → `saveProgress`) идёт без транзакции и без блокировки строки.

**Сценарий.** Два процесса сервера (перезапуск с перекрытием, два контейнера): два действия
одного игрока читают один прогресс — второе затирает открытое первым; два заключения —
второе падает на первичном ключе `player_verdicts` (500). В одном процессе всё верно, тест
«два действия подряд» это держит.

**Уверенность:** вывод (комментарий в коде это признаёт).

**Направление.** `SELECT … FOR UPDATE` по строке игрока в транзакции действия — тогда очередь
в памяти не нужна вовсе.

### 2a-20 · S4 · `api/src/login.ts` · мелочи входа
