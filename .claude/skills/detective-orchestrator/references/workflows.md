# Workflows detective-skills

Каждый workflow: шаги → что передаётся дальше → чем заканчивается. «Автор» —
пользователь, владелец канона.

## DEVELOPMENT — изменить или придумать элемент

Пример: «усилить тайну Габриэля», «добавить улику про время на радио».

1. **orchestrator:** режим, предмет, крупность. Крупная задача → planning-with-files.
2. **detective-architect:**
   - сверка канона и статуса участка (04 §1, §3–§4; файл линии);
   - сборка механизма по цепочке (`shared/mechanism-model.md`) с нужными skills:
     - персонаж → character-management (+ theme-craft, если мотив/моральный конфликт);
     - улика / red herring → genre-craft (`mystery-fair-play.md`), CLUE_INTERACTION_GUIDE (О/Д/И, M-карточки);
     - timeline, алиби → plot-structure + worldbuilding (маршрут, время пути);
     - событие, CCTV, радио → scene-craft + worldbuilding;
     - документ, интервью, переписка (только как функция; текст — отдельной задачей) → voice-style;
     - реальные факты → research, только где ошибка повредит;
   - 2–4 варианта с опытом игрока; impact check; краткий DVC.
3. **Выход:** варианты со статусом «предложено», рекомендация, impact check,
   вопрос автору. Канон не тронут.
4. **Автор выбирает** (или отклоняет / просит иначе).
5. **CANON UPDATE (architect):** правка затронутых 01–04, новый A-номер в
   `DECISIONS_LOG.md`, статус в 04 → **revision-continuity** по затронутым узлам.
6. **Если изменение крупное** (новая цепочка улик, переработка персонажа, меняет
   опоры центрального вывода) → предложить автору detective-auditor и self-eval.
   Playtest не предлагать, пока автор не скажет, что итерация закончена.

## AUDIT — проверить

Пример: «проверь алиби Кейт», «не слишком ли рано видно убийцу», «сломай расследование».

1. **orchestrator:** предмет и режимы аудита (A speedrunner, B skeptic,
   C alternative suspect, D continuity attacker, E fair play, F пакет игрока).
   Если автор не уточнил — выбрать по смыслу, для «найди слабые места» — B+C+D+E.
2. **detective-auditor** (отдельный контекст): передать **аргументом** только
   предмет: что проверять, где это записано (файл и раздел или текст предложения),
   какие режимы. Не передавать доводы, почему решение хорошее.
3. Внутри аудитора: режимы → revision-continuity (continuity, reveal economy) →
   assumption-challenger (скрытые допущения) → self-eval своего отчёта.
4. **Выход:** отчёт находок с severity. Ничего не исправлено.
5. **orchestrator:** пересказать автору без смягчения, спросить, что чинить.
6. Выбранное → DEVELOPMENT (architect предлагает исправления).

## PLAYTEST — итерация закончена

Пример: «версия готова, запусти playtest».

1. **orchestrator:** проверка готовности (SKILL.md §4). Нет пакета игрока —
   остановиться, объяснить, предложить задачу на сборку пакета.
2. Автор запускает `/detective-playtester [профили]` (или прямо просит словами).
3. **detective-playtester:** изолированный игрок в отдельном процессе Claude видит
   только пакет игрока; ведущий выдаёт материалы строго по правилам доступа пакета;
   после прогона — отчёт с метриками.
4. **reader-panel** — только если автор сам вызовет `/reader-panel`; он не
   изолирован от авторского знания и требует `story.md`, поэтому к архиву дела
   обычно не применим.
5. **feedback-triage** (методика): находки профилей → convergent / divergent /
   single; правки не начинать до конца разбора.
6. **detective-auditor**: проблемные места — подтвердить причину по сводам,
   отделить ошибку игрока от дефекта дизайна.
7. **Выход автору:** отчёт прогона + синтез + находки аудитора. Исправления не
   предлагаются, пока автор не выберет, что чинить; затем DEVELOPMENT.

## FEEDBACK REVIEW — отзывы людей или старый отчёт

1. feedback-triage: собрать отзывы в шаблон (`feedback-template.md`), пометить
   источник (человек / симуляция), синтез (`synthesis-template.md`).
2. detective-auditor: для каждой сходящейся находки — причина в дизайне или нет,
   затронутые ID.
3. Автор выбирает, что чинить → DEVELOPMENT.

## Типовые цепочки

```
Изменить персонажа:
orchestrator → architect → character-management → genre-craft → plot-structure
→ (worldbuilding) → решение автора → запись → revision-continuity

Проверить изменение:
orchestrator → auditor[форк: режимы → revision-continuity → assumption-challenger
→ self-eval] → отчёт → автор

Итерация закончена:
orchestrator (готовность) → /detective-playtester → (reader-panel по команде)
→ feedback-triage → auditor → отчёт → автор решает → architect
```

## Чего не делает ни один workflow

- Не меняет канон без выбора автора.
- Не запускает playtest автоматически.
- Не объединяет придумывание и проверку в одном ответе.
- Не создаёт структуру Story Skills и не запускает `story` CLI.
- Не пишет готовые тексты улик, пароли и интерфейс без отдельной задачи.
