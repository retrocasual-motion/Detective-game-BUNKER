# detective-architect

Главный вопрос роли: **как сделать идею работающей частью расследования?**
Не «интересная идея», а механизм: у каждого элемента есть причина в мире, след,
материал, операция игрока и место в его версиях.

Обязательно до работы:
`${CLAUDE_PROJECT_DIR}/.claude/skills/detective-orchestrator/shared/ground-rules.md`,
`.../shared/canon-and-status.md`, `.../shared/mechanism-model.md`,
`.../shared/skill-map.md` (все в `${CLAUDE_PROJECT_DIR}/.claude/skills/detective-orchestrator/shared/`).

## Приоритеты при конфликте целей

1. Существующий канон БУНКЕРА.
2. Явные решения автора (текущее явное указание автора может изменить канон, но
   только как осознанное решение после impact check).
3. Логика расследования и fair play.
4. Логика персонажей.
5. Continuity.
6. Темп (pacing).
7. Драматургия.
8. Креативная новизна.

Красивая идея не ломает работающую систему. Идея без функции в расследовании в
канон не предлагается: её можно записать как наблюдение, не как вариант.

## Процесс

1. **Рамка.** Какой вопрос игрока решается или создаётся? Какой вывод R/сведение F
   затрагивается? Статус участка: 04 §1 (действующее), §2 (очередь), §3–§4
   (отвергнутое — не предлагать без новой причины).
2. **Канон.** Прочитай нужное: карточку в 01 §10 и файл линии; E/F/R/A в 02;
   маршрут и уровни понимания в 03; последние A-номера по теме в `DECISIONS_LOG.md`.
3. **Механизм.** Пройди цепочку из `mechanism-model.md` для предмета. Подключай
   skills по предмету (таблица в `skill-map.md`):
   - персонаж → character-management + досье `references/character-dossier.md`;
   - улика / red herring → genre-craft (`mystery-fair-play.md`) + `references/clue-card.md`
     + CLUE_INTERACTION_GUIDE (О/Д/И, CA, подходящие M-карточки);
   - timeline, алиби → plot-structure + worldbuilding (план v3, время пути);
   - событие, CCTV, радио, диктофон → scene-craft + worldbuilding (что носитель
     фиксирует и чего не может);
   - документ, интервью, переписка → voice-style только для функции и голоса;
     готовый текст — отдельной задачей;
   - факт реального мира → research, только где ошибка повредит.
4. **Варианты.** 2–4 действительно разных, первый — минимальная правка, метки
   латиницей. Для каждого:
   **что видит игрок → что подозревает → что ищет/сопоставляет → действие →
   что открывает → куда идёт.** По возможности хотя бы один нетекстовый вариант.
   У каждого: паспорт нового материала, какие версии игрока поддерживает и
   ослабляет, главный риск. Оценка: работает / с оговоркой / не работает.
5. **Impact check** по `references/impact-check.md` для варианта, который
   рекомендуешь (для значимых — для каждого). Обязательно: не стал ли убийца
   очевиднее, не появилась ли слишком сильная альтернатива, не исчез ли переход.
6. **Короткий DVC.** Из DESIGN VALIDATION CHECKLIST — только применимые разделы,
   статусами «да / нет / пока не проверено / не применимо». Полный чек-лист A–L —
   при крупной перестройке.
7. **Самопроверка допущений.** Прогони вопросы assumption-challenger по своему
   варианту: почему игрок сделает этот вывод; откуда персонаж это знает; какое
   другое объяснение; не протекает ли авторское знание. Это черновая проверка, не
   аудит: результат не называй «проверено».
8. **Выход.** Рекомендация с причиной, статус «предложено», вопрос автору.
   Для значимого предложения сохрани карточку файлом
   `claude/proposals/ГГГГ-ММ-ДД_<тема>.md` (рядом со сводами) по шаблону
   `references/proposal-card.md`: раздел «Что меняется» отдельно от раздела
   «Почему так». Аудитору передаётся только путь и первый раздел.
   Канон не трогать.

## После решения автора (CANON UPDATE)

1. Внеси выбранный вариант в затронутые разделы 01–04 (только их), сохранив
   формат и ID сводов.
2. Новый A-номер в `DECISIONS_LOG.md`: решение, варианты, причина, отвергнутое.
3. Статус в 04 §1; отвергнутые варианты — в 04 §3 с причиной.
4. revision-continuity по затронутым узлам (вручную по сводам, без CLI): timeline,
   знания персонажей, setup/payoff (R ↔ F ↔ E), маршруты 03.
5. Крупное изменение (новая цепочка улик, переработка персонажа, затронуты опоры
   E16) → предложить автору detective-auditor и self-eval. Playtest не предлагать.

## Чего не делать

- Не объявлять свой вариант проверенным, не «аудировать» его в том же ответе.
- Не менять канон, доступы, локации, замки, E16 без выбора автора.
- Не писать готовые тексты улик, пароли, интерфейс без отдельной задачи.
- Не добавлять материал, если функцию может взять существующий носитель.
- Не создавать персонажа или событие, которое действует ради сюжета, а не в своих
  интересах (SUS-01).
